# ملخص إصلاحات مستودع agri-app

التغييرات في هذه النسخة محلية على الفرع `fix/security-hardening`، ولم تُرفع إلى GitHub أو تُنشر على Firebase.

## ما أُصلح في الكود

- استُبدل الاتصال المباشر بـGemini بحزمة `firebase_ai` وFirebase AI Logic، بما في ذلك طلبات النص والصورة. أزيل `GEMINI_API_KEY` من التطبيق وWorkflow؛ لا تضع المفتاح مجدداً في APK أو `--dart-define`.
- فُعّل Firebase App Check في التطبيق: Debug في debug وPlay Integrity في release. يلزم تسجيل التطبيق وإعداد Debug token وتفعيل enforcement في Firebase Console بعد الاختبار.
- أضيفت شاشة خطأ عند فشل تهيئة Firebase، وحُذف طبع FCM token.
- أُضيف `ownerUid` إلى سجل SQLite، وأصبحت القراءة والحذف والمزامنة مقصورة على الحساب الحالي. الصفوف القديمة التي لا تملك UID موثوقاً تُترك معزولة ولا تُنسب تلقائياً لأي حساب.
- أصبحت الطلبات غير المتصلة موسومة بأنها لم تُحلل بعد، فلا تُرفع كتشخيص مكتمل؛ أضيف زر لإعادة إرسال السؤال والصورة من سجل التشخيصات بعد عودة الاتصال.
- شددت قواعد Firestore لملف المستخدم، وأضيف `firebase.json` لربط قواعد Firestore والفهارس، ووُحّدت بعض أخطاء التسجيل. ما زال التسجيل بالبريد الاصطناعي لا يثبت ملكية الهاتف؛ OTP يتطلب تغييراً منفصلاً في التدفق.
- عولجت مدخلات المساحة والحاسبات، وقيود القيم المالية والتوزيعات، وتكرار الخيارات، ونوع `required` ومعرّفات القوالب، وعدّادات الري الصحيحة، وكود لون DXF. أضيفت اختبارات لهذه الحالات.
- أوقفت Workflow إنتاج/رفع ملف keystore كـartifact، وأُزيلت كلمات المرور الثابتة. يستخدم Workflow البناء أسرار GitHub عبر متغيرات البيئة، ولا يرفع إلا APK. أزيل تمرير مفتاح Gemini وأصبح إنشاء الأيقونات يستخدم الاعتماد الموجود في `pubspec.yaml`.
- أصبح التحديث الذاتي يرفض تنزيل APK إذا لم يقدّم `version.json` قيمة SHA-256 صحيحة بطول 64 خانة أو إذا لم تطابق الملف.

## خطوات مطلوبة من مالك المشروع

1. في نسخة موثوقة، شغّل `flutterfire configure` أو انسخ إعدادات تطبيق Android الصحيحة إلى `lib/firebase_options.dart`. قيمة `apiKey` الحالية تبدو مبتورة ولا يمكن تخمين القيم الصحيحة من المستودع. تحقق أيضاً من تطابق `google-services.json` وسر GitHub `GOOGLE_SERVICES_JSON`.
2. في Firebase Console، فعّل Firebase AI Logic، وسجّل Android App Check بـPlay Integrity. سجّل رمز Debug للاختبار فقط، اختبر نسخة debug وrelease، ثم فعّل enforcement وراقب الاستخدام والحصص.
3. ألغِ مفتاح Gemini القديم الذي سبق تضمينه/تمريره في التطبيق، احذف سر `GEMINI_API_KEY` القديم من GitHub، وراجع سجل الاستهلاك. لا يعتبر Firebase API key العام سراً.
4. اعتبر keystore القديم وكلمات مروره مكشوفة. تحقق من Play App Signing وسياسة تحديثات التطبيق قبل إنشاء مفتاح بديل. أنشئ الأسرار الجديدة حسب [دليل توقيع Android](ANDROID_SIGNING_SETUP.md)، ولا تنشر ملف keystore.
5. راجع قواعد Firestore والفهارس في Emulator/Rules Playground وعلى المشروع الصحيح، أنشئ مستند `admins/<UID>` للأدمن يدوياً، ثم انشر القواعد والفهارس بنفسك بعد الاختبار. لم تُنشر تغييرات Firebase من هنا.
6. قبل إصدار APK جديد، أضف SHA-256 للملف إلى `version.json`.

## التحقق والحدود

نجح `git diff --check`، وتم التحقق من صحة JSON في `firebase.json` وملف الفهارس و`version.json`. بيئة التنفيذ لا تحتوي Flutter أو Dart أو Firebase CLI؛ لذلك لم يُشغّل `flutter pub get` أو `dart format` أو `flutter analyze` أو الاختبارات أو بناء APK أو Firebase Emulator. لا تعتمد هذه التغييرات للنشر قبل إجراء هذه الاختبارات في بيئة Flutter موثوقة.

لا يوجد `pubspec.lock` في المستودع، كما ما زالت إجراءات GitHub Actions تشير إلى tags متحركة (`@v2` و`@v4`). هاتان نقطتان متبقيتان لتحسين إعادة إنتاج البناء وسلسلة التوريد؛ يلزم توليد lockfile عبر `flutter pub get` وتثبيت SHAs الموثقة لإصدارات Actions قبل اعتبار البناء قابلاً لإعادة الإنتاج بالكامل.
